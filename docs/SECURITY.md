# Безопасность omarchy-hotspot (этап 2)

Этот документ — спецификация всего кода с правами root и правил защиты. После этапа 2
`crates/helper` и `crates/proto` (протокол помощника) меняются **только** по этому документу.
Новая root-операция = сначала правка этого файла с согласия владельца, потом код.

## 1. Модель угроз

Что защищаем:

- **ПК от гостей.** Устройство, подключённое к раздаче, не должно видеть службы ПК (SSH, файлы,
  docker, http-серверы разработчика) и другие сети ПК (docker0, VPN, вторая LAN).
- **Гостей друг от друга.** Телефон не должен видеть ноутбук соседа.
- **Пароль Wi-Fi.** Никогда не попадает в аргументы процессов, журналы, конфиг плагина, сообщения об ошибках.
- **Систему от нашего root-кода.** Помощник — единственный код с root; он должен быть невозможен
  для использования не по назначению любой программой, запущенной от имени пользователя.
- **Чужие настройки.** Мы не трогаем чужие таблицы nftables, чужие правила ufw, `DEFAULT_*_POLICY`,
  проводной интерфейс, общие настройки NetworkManager.

Кто атакует:

- **Гость раздачи** (знает пароль Wi-Fi): пробует адреса ПК, соседей, LAN; подделывает MAC; шлёт мусор.
- **Локальная программа от имени пользователя** (вредоносный скрипт, плагин): может вызвать
  помощника через pkexec без пароля (см. §4). Должна получить ровно то, что умеет помощник, и ничего больше.
  Поэтому: строгие проверки аргументов, никакого shell, только свои объекты (таблица, файл, правила с комментарием).
- **Ошибка в нашем коде.** Всё, что делает помощник, откатывается `reset`; правила «сваливаются в закрыто»
  (не удалось поставить защиту → раздача выключается).

Что НЕ защищаем: перехват эфира при слабом пароле (пароль генерируется, 16 символов),
злоумышленник с правами root, физический доступ к ПК.

## 2. Помощник `omarchy-hotspot-helper`

Путь: `/usr/lib/omarchy-hotspot/omarchy-hotspot-helper`, владелец `root:root`, права `0755`
(каталог `0755 root:root`). Запуск только через `pkexec` (§4). Помощник проверяет `geteuid() == 0`,
иначе завершается с кодом 2 и сообщением.

Общие правила кода помощника:

- Внешние программы — только `std::process::Command` с массивом аргументов и **абсолютным путём**:
  `/usr/bin/nft`, `/usr/bin/ufw`, `/usr/bin/iw`. Окружение очищается (`env_clear()`),
  задаются только `PATH=/usr/bin`, `LANG=C`, `LC_ALL=C`. stdin — `/dev/null`.
- Никакого `sh -c`, никакой склейки команд из строк. Правила nft передаются через stdin `nft -f -`
  как текст, но **все подставляемые значения** — только значения типов из §2.2, проверенные при разборе.
- Помощник трогает только: таблицу `inet omarchy_hotspot`; правила ufw с комментарием `omarchy-hotspot`;
  файл `/etc/NetworkManager/dnsmasq-shared.d/omarchy-hotspot.conf`; станцию на интерфейсе AP
  (`station-kick`) и страну Wi-Fi (`regdom-set`); чтение `/var/lib/NetworkManager/dnsmasq-<ap>.leases`.
- Журнал: каждая команда (имя и аргументы) и результат пишутся в системный журнал через `/dev/log`
  (syslog, тег `omarchy-hotspot-helper`). Паролей в помощнике нет вообще — он их не принимает.
  Отказы тоже пишутся (этап 8): неверные аргументы командной строки (`rejected arguments`, без текста
  самих аргументов — их присылает вызывающий) и запросы, не прошедшие проверку списков
  (`rejected: <команда>: <причина>`), в том числе в режиме `serve`; там же битые и слишком длинные строки
  (`rejected: bad request`, `rejected: request too long`).
- Ошибки — короткие, на английском, без содержимого чужих файлов. Код выхода: 0 — успех,
  1 — ошибка выполнения, 2 — неверные аргументы/не root.
- Ничего не читает из переменных окружения, кроме того, что делает `clap` для `--help`.
- Одновременно выполняется только один запрос: на время команды берётся эксклюзивный замок
  `/run/omarchy-hotspot-helper.lock` (`flock`). Иначе два `fw-clear` могли бы удалить чужие правила ufw
  из-за сдвига номеров.

### 2.1 Подкоманды

| Подкоманда | Аргументы | Что делает |
|------------|-----------|------------|
| `fw-apply` | `--ap <iface> --uplink <iface> [--approval] [--guests-reach-pc] [--allow <mac>]* [--block <mac>]*` | Целиком пересоздаёт таблицу `inet omarchy_hotspot` (§3.1) и, если ufw активен, добавляет три правила ufw (§3.2). Идемпотентно. Если шаг ufw не прошёл, помощник снимает уже добавленные правила ufw (`ufw::clear`, они переживают перезагрузку) и возвращает ошибку; свежая таблица nft остаётся — она ставится атомарно, это основная защита, и `fw-apply` повторяют на работающей раздаче (этап 8). При включении `start` после ошибки делает `down` и `fw-clear`. |
| `fw-clear` | — | Удаляет таблицу `inet omarchy_hotspot` (если есть) и все правила ufw с комментарием `omarchy-hotspot`. Идемпотентно, не требует раздачи. |
| `fw-block` | `--mac <mac>` | Добавляет MAC в набор `blocked_macs`. Если таблицы нет — ошибка. |
| `fw-unblock` | `--mac <mac>` | Убирает MAC из `blocked_macs` (нет в наборе — не ошибка). |
| `fw-allow-add` | `--mac <mac>` | Добавляет MAC в набор `allowed_macs` (одобрение устройства, этап 5). |
| `fw-allow-remove` | `--mac <mac>` | Убирает MAC из `allowed_macs`. |
| `station-kick` | `--ap <iface> --mac <mac>` | `iw dev <ap> station del <mac>` — отключает устройство от точки доступа. Без блокировки оно может подключиться снова; для запрета сначала `fw-block`. |
| `regdom-set` | `<CC>` | `iw reg set <CC>` — регуляторный домен (страна) для Wi-Fi. |
| `dns-set` | `<ip> [<ip> ...]` (1–4) | Пишет файл `dnsmasq-shared.d/omarchy-hotspot.conf`: `no-resolv` + `server=<ip>` на каждый адрес. Вступает в силу после перезапуска раздачи (это делает приложение). Файл действует на **все** shared-подключения NetworkManager (так устроен NM; обойти нельзя). |
| `dns-clear` | — | Удаляет этот файл (нет файла — не ошибка). |
| `leases-read` | `--ap <iface>` | Печатает в stdout содержимое `/var/lib/NetworkManager/dnsmasq-<ap>.leases` (нет файла — пустой вывод). `--ap` должен быть беспроводным (`phy80211`; режим AP не требуется — окно читает аренды и при выключенной раздаче), чтобы не читать аренды чужих shared-подключений (этап 8). Разбор — в `core`, не в помощнике. |
| `serve` | — | Режим службы (этап 5): читает запросы JSON построчно из stdin, отвечает построчно в stdout (§5). |

Переименование относительно `PLAN.md`: вместо `fw-pending-add/remove` — `fw-allow-add/remove`.
Причина: режим одобрения сделан как **белый список** (`--approval`: пропускать в интернет только MAC из
`allowed_macs`), а не как «блокировать ожидающих». Иначе между подключением устройства и командой службы
есть окно, когда трафик уже идёт. С белым списком окна нет: новое устройство получает адрес (DHCP) и DNS,
но не интернет, пока служба не вызовет `fw-allow-add`.

### 2.2 Типы аргументов и проверки

Синтаксические проверки — в крейте `omarchy-hotspot-proto` (`crates/proto`, в ядре доступен как
`core::helper_proto`; общие для приложения, службы и помощника, тесты там же). Помощник зависит только
от этого крейта, а не от всего ядра (этап 8): в root-бинарнике 36 крейтов вместо 122. Системные проверки (существование, режим) — только в помощнике.

| Тип | Синтаксис | Дополнительно в помощнике |
|-----|-----------|---------------------------|
| `Iface` | `^[A-Za-z0-9_.-]{1,15}$`, не начинается с `-` или `.`, не `lo` | `/sys/class/net/<iface>` существует. Для `--ap`: есть `/sys/class/net/<iface>/phy80211` и `iw dev <iface> info` содержит `type AP`. Для `--uplink`: не совпадает с `--ap`, не мост (`/sys/class/net/<iface>/bridge` нет — иначе гости попали бы в контейнеры/ВМ; этап 8) и не беспроводной в режиме AP. |
| `Mac` | `^[0-9a-f]{2}(:[0-9a-f]{2}){5}$` после перевода в нижний регистр; не `00:00:00:00:00:00`, не multicast/broadcast (младший бит первого байта = 0) | — |
| `CountryCode` | две латинские буквы, приводятся к верхнему регистру, есть в встроенном списке ISO 3166-1 alpha-2 (плюс `00` — «мировой» домен) | — |
| `DnsServer` | `IpAddr` (v4 или v6) через `std::net`; не unspecified, не multicast, не loopback, не broadcast, не link-local; не IPv6 с вложенным IPv4 (`::ffff:a.b.c.d`, `::a.b.c.d` — обход проверки loopback; этап 8) | список 1–4 адресов, без повторов |
| списки `--allow/--block` | ≤ 256 элементов каждый, без повторов | — |

Всё, что не подходит — ошибка до любого действия (сначала проверяются ВСЕ аргументы, потом
выполняется команда). Тесты на: `;`, `$(…)`, пробелы, переводы строк, юникод, слишком длинные строки,
`../`, пустые строки, MAC в верхнем регистре, широковещательный MAC.

## 3. Правила брандмауэра

### 3.1 nftables — таблица `inet omarchy_hotspot`

Создаётся `fw-apply` одной атомарной транзакцией `nft -f -` (сначала `table inet omarchy_hotspot {}`
и `delete table`, потом полное определение — так повторный вызов заменяет старую версию).
Значения `<ap>`, `<uplink>` и MAC берутся только из проверенных типов §2.2.

```
table inet omarchy_hotspot {
    set blocked_macs { type ether_addr; }
    set allowed_macs { type ether_addr; }

    chain input {
        type filter hook input priority filter; policy accept;
        iifname "<ap>" jump from_ap_input
    }
    chain from_ap_input {
        ether saddr @blocked_macs drop
        ct state established,related accept
        ct state invalid drop
        udp dport 67 accept          # DHCP
        udp dport 53 accept          # DNS
        tcp dport 53 accept
        drop                         # нет при --guests-reach-pc
    }

    chain forward {
        type filter hook forward priority filter; policy accept;
        iifname "<ap>" jump from_ap_forward
    }
    chain from_ap_forward {
        ether saddr @blocked_macs drop
        oifname != "<uplink>" drop   # в т.ч. AP → AP, AP → docker0, AP → VPN
        ether saddr != @allowed_macs drop   # только при --approval
    }
}
```

Принципы:

- `drop` в любой таблице окончателен, `accept` у нас **не отменяет** drop у ufw/чужих таблиц. Поэтому
  наши `accept` — только внутри своей цепочки; разрешения для ufw делаются через ufw (§3.2).
- NAT (`masquerade`) и включение пересылки делает NetworkManager (таблица `ip nm-shared-<ap>`). Не дублируем.
- `--guests-reach-pc` (продвинутый режим, конфиг `hotspot.guests_can_reach_pc`) убирает только наш
  финальный `drop` во входящей цепочке. Правила ufw пользователя при этом продолжают действовать —
  мы ничего в ufw не открываем сверх §3.2.
- IPv6 у профиля выключен (`ipv6.method disabled`); семейство `inet` на всякий случай покрывает и v6.
- ARP — отдельное семейство, наши правила его не трогают (адресация в подсети работает).
- Изоляция гостей на уровне Wi-Fi (`ap-isolation yes`, D4) остаётся; `oifname != uplink drop` — второй рубеж.

### 3.2 ufw

Проверка активности — `ufw status` (первая строка `Status: active`). Если активен, `fw-apply` добавляет
(если такой строки с комментарием `omarchy-hotspot` ещё нет в `ufw status`):

```
ufw allow in on <ap> proto udp from any port 68 to any port 67 comment omarchy-hotspot
ufw allow in on <ap> proto udp to any port 53 comment omarchy-hotspot
ufw allow in on <ap> proto tcp to any port 53 comment omarchy-hotspot
ufw route allow in on <ap> out on <uplink> comment omarchy-hotspot
```

`fw-clear` удаляет наши строки (оканчиваются на `# omarchy-hotspot`) **по одной**: перечитать
`ufw status numbered` → удалить строку с наибольшим номером `ufw --force delete <n>` → повторить, пока строк нет.
Чужие правила и политики не трогаем. Правила ufw переживают перезагрузку и падение приложения, таблица nft — нет:
`fw-apply` не создаёт дубликаты, `off`/`reset` убирают правила даже если выключение раздачи не удалось,
установщик (§8) добавляет `fw-clear` при загрузке системы.

### 3.3 Известные ограничения (осознанно)

- Списки по MAC (`blocked_macs`, `allowed_macs`) обходятся подменой MAC гостем, знающим пароль. Это фильтр
  «по-хорошему», не криптографическая защита; настоящая защита — смена пароля.
- В режиме `--approval` неодобренное устройство получает DNS от ПК (иначе телефон считает сеть «без интернета»
  и отключается). Через DNS теоретически возможен туннель (iodine) — принимаем как компромисс.
- Гости достигают локальной сети за uplink (роутер, другие устройства домашней LAN) — так устроена раздача.
- Между `up` (точка доступа в эфире) и `fw-apply` есть окно в секунды без таблицы nft (ufw пользователя при этом
  работает как обычно). `fw-apply` требует режим AP на интерфейсе, поэтому применить раньше нельзя.
- Если раздачу включили без службы, а служба поднялась позже, режим одобрения она включит примерно через
  две секунды после того, как увидит раздачу (этап 5). В это окно новое устройство успело бы выйти в интернет.
  Обычный путь (`on` в CLI или пробел в окне) сначала поднимает службу и применяет правила сразу — окна нет.
- Исходящие multicast-анонсы ПК (mDNS) не фильтруются: гость может узнать имя хоста.

### 3.4 Данные, которые присылают гости (этап 4)

- Имя устройства в списке берётся из аренд dnsmasq, а его сообщает по DHCP само устройство —
  это недоверенные данные. Перед показом имя чистится (`core::net::leases::sanitize_hostname`):
  убираются управляющие символы (escape-коды терминала), невидимые символы и переворот текста,
  длина обрезается до 24 символов. Имя нигде не подставляется в команды.
- Строки `iw station dump` и `ip -j neigh` разбираются без паники: плохой MAC, битый JSON и
  неизвестные поля просто пропускаются, ошибка опроса не показывается пользователю (только в журнал).
- Опрос устройств root не требует; помощник вызывается только за арендами и не чаще раза в 15 секунд.

## 4. Polkit

Файл `/usr/share/polkit-1/actions/org.omarchy.hotspot.policy` (владелец root, `0644`), одно действие
`org.omarchy.hotspot.helper`:

- `allow_any = no`, `allow_inactive = no`, `allow_active = yes`;
- аннотация `org.freedesktop.policykit.exec.path = /usr/lib/omarchy-hotspot/omarchy-hotspot-helper`;
- без `exec.allow_gui`.

Решение владельца (11.09.2026): `allow_active = yes`. Известный компромисс: `regdom-set` меняет регуляторный домен
всего Wi-Fi ПК (не только раздачи) — единственная операция с эффектом за пределами раздачи; при желании ужесточить —
вынести в отдельный бинарник со своим action `auth_admin_keep`. Обоснование: фоновая служба (этап 5) одобряет
устройства и снимает правила без участия пользователя; панель и меню включают раздачу одним кликом.
Это допустимо ТОЛЬКО потому, что помощник выполняет узкий, проверенный набор операций над своими объектами
(§2), не принимает произвольных путей, команд и паролей. Запасной вариант, если владелец передумает —
`auth_admin_keep` (одна правка в policy-файле, код не меняется).

Приложение вызывает `pkexec /usr/lib/omarchy-hotspot/omarchy-hotspot-helper <аргументы>`.
Коды `pkexec`: 126 — пользователь отказался, 127 — не разрешено политикой → понятная ошибка
«нет прав на защиту раздачи». Если файла помощника нет — приложение сообщает «защита не установлена»
и раздачу не включает (с этапа 7; выключение и `reset` без помощника работают).

## 5. Режим `serve` (для службы, этап 5)

Служба запускает `pkexec … serve` один раз на всё время раздачи и общается по stdin/stdout.

- Запрос — одна строка JSON ≤ 32 КиБ без перевода строки (`SERVE_MAX_LINE`; этап 8, было 8 КиБ — самый
  большой допустимый `fw-apply` с 256 + 256 MAC занимает около 10,4 КиБ, тест это держит):
  `{"cmd":"fw-block","mac":"aa:bb:cc:dd:ee:ff"}` (поля как в §2.1,
  имена в kebab-case, тип `HelperRequest` в `crates/proto`). Проверки — те же, что для CLI
  (общий обработчик).
- Ответ — одна строка: `{"ok":true,"output":"…"}` или `{"ok":false,"error":"…"}`.
- Строка длиннее лимита, не-JSON, неизвестная команда → ответ с ошибкой, соединение продолжается.
  Остаток длинной строки выбрасывается только если перевод строки ещё не прочитан (этап 8: раньше строка
  ровно на пределе съедала следующий запрос, и служба с помощником ждали друг друга вечно).
- Служба проверяет длину запроса до отправки. Любой сбой обмена (ответ длиннее предела, не-JSON,
  обрыв) закрывает канал: следующий запрос откроет новый, ответы не перепутаются с запросами.
- EOF на stdin → помощник завершает работу с кодом 0. `serve` внутри `serve` запрещён.
- Сокет службы для окна (`$XDG_RUNTIME_DIR/omarchy-hotspot/daemon.sock`, каталог `0700`, сокет `0600`):
  служба принимает MAC только через `helper_proto::Mac` и передаёт помощнику готовые типы;
  запросы от окна ≤ 64 КиБ; пароль по сокету не ходит (DECISIONS §6).
- Кто подключился к сокету, проверяется по `SO_PEERCRED`: uid должен совпадать с uid службы
  (каталог `0700` и так закрывает доступ, это вторая линия).
- Ответ помощника служба читает с пределом 1 МиБ (`core::helper::SERVE_MAX_RESPONSE`): самый большой
  ответ — файл аренд dnsmasq.
- Что делает служба (этап 5) и ничего сверх того: `fw-apply` при включённой раздаче (режим одобрения),
  `fw-allow-add`/`fw-allow-remove`, `fw-block`/`fw-unblock`, `station-kick`, `leases-read`, `fw-clear`
  (через `hotspot::stop` при авто-выключении). Новых root-операций этап 5 не добавил.
- Имена устройств в уведомлениях: имя придумывает гость, поэтому кроме очистки при разборе аренд
  (§3.4) в тексте уведомления экранируются `&`, `<`, `>` — серверы уведомлений понимают разметку,
  а перед текстом в `notify-send` ставится `--`, чтобы имя не разобрали как ключ командной строки.
- Единственность службы держит `flock` на `$XDG_RUNTIME_DIR/omarchy-hotspot/daemon.lock`: только
  владелец замка убирает оставшийся от прошлого раза сокет, поэтому две службы не могут работать разом.
- Конфиг пишут трое (окно, CLI, служба), поэтому «прочитать → изменить → записать» выполняется под
  замком `config.toml.lock` (`core::config::update`), и каждый меняет только свои поля. Правило
  брандмауэра и запись в конфиг меняются под одним замком: либо оба, либо ничего.
- Число новых устройств, о которых служба спрашивает и шлёт уведомления за сеанс, ограничено
  (32 вопроса, 10 уведомлений): гость со сменой MAC не должен заваливать рабочий стол.
- **Ограничение схемы:** канал `serve` живёт весь сеанс раздачи. При нынешней политике
  (`allow_active = yes`, §4) это не даёт новых прав: любой процесс пользователя и так может вызвать
  помощника. Но если владелец когда-нибудь переключит политику на `auth_admin`, долгоживущий канал
  станет усилителем — одна аутентификация откроет все операции помощника на весь сеанс. При таком
  переходе схему службы надо пересмотреть (канал на одну операцию либо повторный запрос пароля).

## 6. Лимит скорости — удалён (этап 9, решение владельца 14.09.2026)

Подкоманды `tc-limit`/`tc-clear`, тип `Kbps`, feature `tc`, раздел `[limits]` конфига и запрос службы `SetLimit`
удалены целиком. Помощник больше не знает `/usr/bin/tc`. Старый раздел `[limits]` в конфиге молча пропускается.

## 7. Пароль Wi-Fi

- Хранит только NetworkManager (`psk-flags 0`, системный профиль).
- Профиль ограничен пользователем: `connection.permissions user:<имя>` (имя — из базы пользователей по uid);
  если имя определить нельзя, профиль не создаётся (общий профиль читали бы все пользователи ПК).
- Запись пароля — через D-Bus (`zbus`, шина system): `Settings.GetConnectionByUuid` →
  `Connection.GetSettings` → добавить `802-11-wireless-security.psk` → `Connection.Update2(flags=to-disk)`.
  Аргументы процессов при этом не используются. Чтение — `nmcli -s -g 802-11-wireless-security.psk`
  (пароль в stdout процесса, а не в аргументах — допустимо).
- В коде пароль живёт в `Secret` (Debug = `***`, затирается при уничтожении); функции, где он проходит,
  не логируют аргументы и не сохраняют stderr внешних программ.

## 8. Требования к установщику (этап 7)

| Что | Куда | Владелец / права |
|-----|------|------------------|
| `omarchy-hotspot-helper` | `/usr/lib/omarchy-hotspot/omarchy-hotspot-helper` | `root:root 0755`, каталог `root:root 0755` |
| `org.omarchy.hotspot.policy` | `/usr/share/polkit-1/actions/` | `root:root 0644` |
| `omarchy-hotspot` (приложение) | `~/.local/bin/omarchy-hotspot` | пользователь, `0755` |

Установщик также ставит системный unit `/etc/systemd/system/omarchy-hotspot-cleanup.service`
(`root:root 0644`, `Type=oneshot`, `WantedBy=multi-user.target`), который при загрузке выполняет
`/usr/lib/omarchy-hotspot/omarchy-hotspot-helper fw-clear` (уборка правил ufw после аварии; новых root-операций нет).
При установке unit только включается (`enable`), не запускается — иначе снял бы правила работающей раздачи.
Песочница unit (этап 8): `ProtectSystem=strict` с `ReadWritePaths=-/etc/ufw /run` (дефис — путь необязателен: без ufw каталога нет) (ufw переписывает `user.rules`,
помощник держит замок в `/run`), `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, `ProtectKernelTunables`,
`ProtectControlGroups`, `RestrictAddressFamilies=AF_UNIX AF_NETLINK AF_INET AF_INET6` (nft — netlink, syslog — unix).
Осознанное ограничение установки из исходников: помощник собирается в папке пользователя и копируется под
`sudo`. Вредоносная программа, уже работающая от имени пользователя, могла бы подменить его до копирования —
но она так же может подменить сам `install.sh`. Защита от этого — пакет AUR (этап 9).
Перед установкой `install.sh` проверяет, что помощник, его каталог, `/usr/lib`, `/usr` и `/` принадлежат root
и не записываемы группой/другими; иначе останавливается. Политика polkit ставится только после этой проверки.

Установщик: проверяет, что помощник не записываем никем, кроме root (иначе polkit-разрешение даёт root
любому, кто сможет подменить файл); ставит файлы через `install -o root -g root -m …` под `sudo`, показав
команды заранее. Удаление: `fw-clear`, `dns-clear`, удалить оба файла и каталог. Текст policy-файла —
`packaging/org.omarchy.hotspot.policy` в репозитории (единственный источник).

### 8.1 Пакет AUR (этап 9)

Новых root-операций нет. Все файлы ставит `pacman`, владелец `root:root`:

| Что | Куда | Права |
|-----|------|-------|
| приложение | `/usr/bin/omarchy-hotspot` | `0755` |
| помощник | `/usr/lib/omarchy-hotspot/omarchy-hotspot-helper` (тот же путь, что в политике) | `0755` |
| политика polkit | `/usr/share/polkit-1/actions/org.omarchy.hotspot.policy` | `0644` |
| служба уборки | `/usr/lib/systemd/system/omarchy-hotspot-cleanup.service` + ссылка в `multi-user.target.wants/` | `0644` |
| служба пользователя | `/usr/lib/systemd/user/omarchy-hotspot.service` (`ExecStart=/usr/bin/omarchy-hotspot daemon`), не включена | `0644` |
| настройка Omarchy | `/usr/share/omarchy-hotspot/{install.sh,uninstall.sh,manifest.json,BarWidget.qml}` | `0755` / `0644` |
| обёртки | `/usr/bin/omarchy-hotspot-setup`, `/usr/bin/omarchy-hotspot-remove` (`exec` скрипта выше) | `0755` |

- Служба уборки включена ссылкой из пакета (страховка защиты, не функция по желанию) и при установке не
  запускается — как в §8. Служба пользователя из исходников (`~/.config/systemd/user`) имеет приоритет над
  пакетной, поэтому `omarchy-hotspot-setup` предлагает убрать старые `~/.local/bin/omarchy-hotspot` и файл службы.
- `install.sh` и `uninstall.sh` различают режим по своему каталогу: `/usr/share/omarchy-hotspot` — пакет.
  В режиме пакета они **не вызывают `sudo`** и не трогают системные файлы: только конфиги пользователя
  (с согласием, маркерами и копиями `.bak-<дата>`, как в §8) и `reset` приложения.
- `pre_remove` (от root, до удаления файлов; при обновлении не вызывается), все программы по абсолютным путям:
  1. `nmcli connection down` и `connection delete id omarchy-hotspot` — только свой профиль. Профиль удаляется:
     включённый потом вручную, он раздавал бы интернет уже без помощника и правил изоляции;
  2. `pkill -f '^/usr/lib/omarchy-hotspot/omarchy-hotspot-helper serve$'` — процесс root службы не переживает
     удаление пакета (не `pkill -x`: имя процесса обрезается до 15 символов и совпало бы с программой);
  3. если раздача всё ещё активна (`nmcli -g GENERAL.STATE connection show --active`), правила **не** снимаются
     (как `off`, §10) и выводится предупреждение; иначе помощник `fw-clear` и `dns-clear`.
  Конфиги пользователя (`~/.config/omarchy-hotspot`, вставки Omarchy) не трогаются: у `pacman` нет пользователя —
  для этого `omarchy-hotspot-remove` до удаления пакета.
- Пакет и установка из исходников конфликтуют по путям помощника и политики: `pacman` откажет, пока не выполнен
  `./uninstall.sh`. В обратную сторону `./install.sh` и `./uninstall.sh` из исходников останавливаются, если
  помощник, его каталог или политика принадлежат пакету (`pacman -Qqo`) или пакет `omarchy-hotspot` установлен:
  иначе `sudo` перезаписал или удалил бы файлы пакета.
- Старый значок (id `omarchy-hotspot`, до публикации) и новый удаляются, только если `manifest.json` в каталоге
  совпадает по `id` и `author` — чужой плагин с тем же id не трогается.
- Ограничение §8 о подмене помощника при сборке пакет **не снимает**: AUR-помощники (`yay`) собирают
  от имени пользователя в его папке. Пакет убирает другое — копирование под `sudo` из каталога сборки
  выполняет `pacman` по списку файлов пакета, а не скрипт, который можно подменить вместе с программой.
- Сборка: `cargo fetch --locked`, затем `--frozen` (зависимости только из `Cargo.lock`, сеть при сборке не нужна).
  Источник — архив тега `v$pkgver` на GitHub; перед публикацией в AUR `sha256sums` заменяется на настоящую сумму.

## 5.1 Продвинутый режим (этап 6)

Новых root-операций и изменений в `crates/helper` нет. Что изменилось в том, **когда** и **кем** зовётся помощник:

- `on` сначала делает все проверки без изменений в системе (`resolve`, источник интернета, `firewall_request`),
  и только потом, перед `up`, вызывает `regdom-set` (если `hotspot.country` задан и отличается от `iw reg get`) и
  `dns-set` (если `network.dns` не пуст) или `dns-clear` (если пуст, а наш файл остался). Страна и DNS
  проверяются типами `CountryCode`/`DnsServer` + `check_dns_list` до любого вызова помощника; ошибка
  любого шага — раздача не включается. Без помощника оба шага пропускаются.
- Сохранение настроек из окна при включённой раздаче, если нужен перезапуск: сначала `resolve` (проверка
  без изменений), потом `off` (`down` + `fw-clear`) и `on` (с шагами выше и `fw-apply`). Настройки,
  которые не удалось применить, в конфиг не пишутся.
- `hotspot.guests_can_reach_pc` и `access.approval_required` меняются без перезапуска: служба держит
  «с какими настройками применены правила» (`RulesKey`) и сама повторяет `fw-apply`, если они разошлись
  с конфигом (в ключе ещё источник интернета из настроек). Теперь служба применяет правила один раз в каждом
  сеансе раздачи в любом случае (раньше — только при режиме одобрения). Без службы окно само делает `fw-apply`
  с режимом одобрения из настроек (не «без одобрения»: иначе сняло бы белый список, поставленный службой).
- При перезапуске из окна конфиг пишется между `off` и `on` и служба получает `ReloadConfig` до `on`: иначе её
  «первое применение правил» могло пройти по старому конфигу (например, со старым источником интернета).
  Если после `off` раздачу успел включить кто-то другой (`AlreadyOn`), это ошибка, а не «сохранено».
- Сохранение переносит только поля, которые пользователь изменил в черновике (`merge_changed`, трёхстороннее
  слияние со свежим файлом): изменения службы и CLI (одобрение, списки MAC) окно не откатывает.
- Окно не пишет «одобрение включено», если раздача работает, а службы нет: показывает, что одобрение не действует.
  Таймер и простой без службы — предупреждение при сохранении.
- Источник интернета выбирается только из типов ethernet/wifi/wireguard/tun/ppp/gsm/cdma/bond/vlan/team/adsl:
  мосты (docker0, virbr0) не предлагаются. DNS вида `::ffff:a.b.c.d` не принимается (обход проверки loopback).
- Автозапуск не включает раздачу, если помощник не установлен (иначе она работала бы без брандмауэра).
- Раздел «Устройства» в окне: `allow`/`block`/`unblock`/`kick` идут через службу; без службы — те же
  `core::access::apply` под замком конфига и `station-kick`, что и CLI `access` (§5).
- Подсеть: только частные диапазоны (`Ipv4Net::is_private_host`: 10/8, 172.16/12, 192.168/16, не адрес
  сети и не широковещательный) — проверка в `Hotspot::resolve`, её не обойти правкой конфига.
- IPv6 остаётся выключенным (решение владельца 13.09.2026): раздача IPv6 потребовала бы новых разрешений
  во входящей цепочке (ICMPv6/RA/DHCPv6) в помощнике. В окне — строка «только для чтения».
- Журнал в окне: `journalctl --user -u omarchy-hotspot.service` и `journalctl -t omarchy-hotspot-helper _UID=0`
  (без root, массив аргументов; `_UID=0` отсекает подделку через `logger -t`); управляющие символы заменяются
  пробелом, невидимые и переворачивающие текст — удаляются.
- Подсеть раздачи не должна пересекаться с сетями других интерфейсов (этап 8): иначе трафик ПК к адресам LAN
  или VPN ушёл бы гостям, а гость может занять такой адрес. `Hotspot::resolve` читает
  `ip -j -4 route show table all` (без root) и отказывает (`SubnetConflict`), если подсеть пересекается с
  обычным маршрутом другого интерфейса или с его собственным адресом (`local`, как /32 — VPN «весь трафик»
  не ставит маршрут к своей сети). У маршрутов с несколькими путями проверяется каждый `nexthops[].dev`.
  Не считаются: маршруты самого адаптера точки доступа и `lo`, `broadcast`/`anycast`/`multicast`,
  маршруты без интерфейса (`blackhole`, `unreachable`) и маршруты шире /8 (VPN ставит `0.0.0.0/1` + `128.0.0.0/1`
  вместо маршрута по умолчанию). Маршруты не прочитались — раздача не включается. VPN, поднятый уже после
  включения раздачи, не отслеживается (осознанное ограничение).
- Сообщения «заблокировано/разрешено/отключено» в окне появляются только после ответа «готово» (от службы —
  по очереди ожидаемых ответов, служба отвечает на каждый запрос один раз и по порядку; без службы — после
  помощника). При ошибке показывается только ошибка.
- Автозапуск при входе: `systemctl --user enable|disable omarchy-hotspot.service`. Служба включает
  раздачу один раз за вход (метка `$XDG_RUNTIME_DIR/omarchy-hotspot/autostart-done`) и **не** включает её,
  если Wi-Fi-адаптер подключён к сети как клиент — только уведомление. `reset` делает `disable`.

## 9. Wi-Fi

- По умолчанию WPA3: `key-mgmt sae`, `pmf required` (`3`), `proto rsn`, `pairwise/group ccmp`.
- Совместимый режим: `key-mgmt wpa-psk`, `pmf optional` — на деле WPA2/WPA3 (DECISIONS §11).
- Никогда: открытая сеть, WEP, WPA1, TKIP, `pmf disable`.
- `ap-isolation yes` (по умолчанию; выключается в продвинутом режиме), `ipv6.method disabled`,
  `connection.autoconnect no`, канал задаётся явно.
- Ширина канала (этап 6): `802-11-wireless.channel-width` = `20mhz|40mhz|80mhz` (80 только на 5 ГГц,
  иначе 40), неизвестное значение → `auto`.

## 10. Порядок действий приложения

- `on`: профиль → `up` → `fw-apply`. Без помощника `start` отказывает сразу, до любых изменений (§4). Не удалось `fw-apply` → `down` и ошибка:
  раздача без защиты не остаётся включённой.
- `off`: `down` и `fw-clear`. Если `down` не удался, а раздача по-прежнему включена, правила **не** снимаются
  (этап 6, находка ревью): иначе раздача осталась бы без защиты. В остальных случаях `fw-clear` выполняется
  и после ошибки `down`.
- `reset`: `down` → удалить профиль → `fw-clear` → `dns-clear` → конфиг; все шаги
  выполняются независимо, возвращается первая ошибка. Шаги помощника выполняются и без NetworkManager.
  Регуляторный домен (`regdom-set`) `reset` сознательно не возвращает: он сбрасывается перезагрузкой.
- `set …` при включённой раздаче: повторный `up` (правила остаются, таблица привязана к имени интерфейса).
  Если адаптер из настроек не совпадает с адаптером работающей раздачи, `apply` отказывает
  (`AdapterChanged`, этап 8): иначе точка доступа переехала бы, а правила остались на старом имени.
- `on`: если `fw-apply` не прошёл, после `down` вызывается `fw-clear` (этап 8): помощник мог поставить
  часть правил (таблицу nft, часть правил ufw — они переживают перезагрузку) до ошибки.
- `on`: имя источника интернета из конфига (`network.uplink_interface`) принимается, только если оно есть
  среди `uplink_candidates()` (подключённые интерфейсы без мостов, §5.1); иначе `Config`-ошибка (этап 8).
- `on`: если `up` вернул ошибку (например, тайм-аут `nmcli --wait`), выполняется `down` (этап 8):
  NetworkManager мог продолжить включение, и раздача появилась бы позже без `fw-apply`.
- Служба на `allow`/`block`/`unblock` при неизвестном состоянии раздачи (опрос NM не удался) или в
  состоянии «включается» отвечает ошибкой, а не «готово» (этап 8).
- Замок действий (этап 8): `start`/`stop`/`apply`/`reset` берут `flock` на
  `$XDG_RUNTIME_DIR/omarchy-hotspot/hotspot.lock` (каталог `0700`, файл `0600`) на время всего действия, вместе
  с проверкой «уже включена?». Без замка одновременные `off` и `on` (панель, окно, служба) могли снять
  правила после их установки. Ждём до 120 с, потом `Busy`. Замок не держится во время запросов к службе
  (служба сама берёт его для авто-выключения). `reset` при занятом замке выполняется без него. Без
  `XDG_RUNTIME_DIR` — без замка (предупреждение в журнале).
